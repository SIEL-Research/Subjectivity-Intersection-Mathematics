# Technical Specification

## Audit layers

### Provenance layer

The runner verifies the Riemann Git commit and remote, the SHA-256 values of the pinned Riemann files, and the SHA-256 value of the exact Advaita source file. A local path is never treated as authority.

### Signed-FNIZ layer

The runner imports the frozen implementation and checks:

- eight signed states;
- four base operations;
- 256 ordered operation cells;
- distinct positive and negative zero;
- subtraction as addition with oriented reversal for all 64 ordered pairs;
- division as multiplication by formal reciprocal for all 64 ordered pairs.

Packet equality is exact tuple equality in the source-defined canonical order.

### Advaita layer

The runner performs exact-text checks for:

- the four named arithmetic operations;
- the statement that operator history is data;
- the statement that the full recovered rule set requires additional restoration work;
- the carrier equation `X=(A,B)` in its LaTeX form.

The audit separately searches for an integration-specific derivation of subtraction or division. An absent statement is reported as absent.

### D12 layer

The runner verifies that integer translations modulo twelve form a cyclic group, enumerates the subgroup generated by every ordered pair `(a,m)`, and verifies that every subgroup order divides twelve.

It also checks that the moving Paper 5.3 projector exposes twelve deck translations, that all twelve translated mode sets are distinct, and that their union covers all twelve modes.

### DVJ layer

The frozen positive DVJ roots and native transfer are evaluated at the registered parameters:

- 0.5;
- 1.0;
- 2.0; and
- 5.0.

At each parameter the audit checks forward transfer, inverse transfer, nonzero carrier value, reciprocal determinant one, and twelve-step D12 central-holonomy closure. The numerical tolerance is `1e-40` with mpmath 1.3.0 precision fixed at 80 decimal digits for evaluation and 90 digits for root construction.

### Connector layer

Python files under `src/d12rg_riemann` are parsed with the standard-library AST. The runner records files that jointly reference all three required families:

- FNIZ;
- DVJ transfer or holonomy;
- D12 deck or moving-projector action.

An executable connector requires more than co-occurring prose. It must contain an AST-visible definition or import/use chain that maps the FNIZ-side input to the DVJ/D12-side output. The runner records candidates but does not infer missing semantics from names.

The Advaita source and pinned Riemann documents are also searched for explicit cross-layer formulae. Textual co-occurrence is reported but cannot on its own establish an executable connector.

## Conditional family and pruning

The conditional operation-to-deck family is generated from the two primitive offsets `(a,m)` in `C12`. Derived offsets are fixed to `(-a mod 12, -m mod 12)`. The full family size is therefore 144.

The following counts are frozen:

- initial unconstrained operation-offset assignments: `12^4 = 20,736`;
- after primitive/derived constraints: `12^2 = 144`;
- after the conditional Lagrange constraint: reported from execution;
- after any explicit source anchor: reported from execution.

Because every subgroup of C12 necessarily has order dividing twelve, Lagrange's theorem is expected to validate the conditional group family but need not prune it. The observed pruning count will be reported rather than presumed.

No member of this family is selected in Phase 1.

## Primary decision logic

If an explicit executable connector exists and exactly one conditional rule agrees with it, classify `UNIQUE_SOURCE_DERIVED_RULE`.

If an explicit source mapping exists but several rules remain, classify `MULTIPLE_SOURCE_ADMISSIBLE_RULES`.

If the connector premise is explicit but the registered constraints retain all 144 conditional rules, classify `SOURCE_CONSTRAINTS_DO_NOT_NARROW`.

If explicit source constraints eliminate all rules, classify `NO_ADMISSIBLE_RULE`.

If no explicit FNIZ-to-DVJ-to-D12 mapping premise is present, classify `INCOMPLETE_SOURCE_DEFINITION`, regardless of whether a newly written bridge could be constructed.

## Failure behavior

The runner exits nonzero for provenance mismatch, missing required source, source hash mismatch, manifest mismatch, failed registered finite identity, failed D12 group law, failed DVJ source check, or incomplete output writing.

It exits zero for a complete audit whose classification is non-unique, non-narrowing, or source-incomplete.
